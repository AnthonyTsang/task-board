  near-white text on the browser's default white page. That's your "too light".
  - Both form inputs set dark:bg-neutral-900 with no matching dark:text-* — so a
  near-black box with black text. That's your "black on black".

  Worth noting the screenshot showed more damage than you'd spotted: all three
  task titles and the "All" tab were also invisible. The descriptions and "3 of
  3 remaining" survived only by accident — they use a mid-grey that happens to
  read on white.

  The fix, two parts:

  1. index.css now sets the page surface for both schemes — white/dark-text by
  default, neutral-950/light-text under prefers-color-scheme: dark. Tailwind's
  preflight derives ::placeholder from currentColor, so placeholders follow
  automatically.
  2. Each input's background is now paired with an explicit text colour, in both
  schemes.

  I verified in the browser rather than assuming: heading, titles, tabs, typed
  text, and the completed strikethrough all legible. I also confirmed the built
  CSS contains both the light rule and the dark override, so this isn't a fix

● Done — two commits on feat/task-board.

  What it does. On SIGINT/SIGTERM the server stops accepting connections, lets
  in-flight requests finish, closes the Sequelize pool, and exits 0. A 10s timer
  bounds the wait and exits 1 rather than hanging. Previously a signal killed
  the process mid-request with the pool still open.

  Two things are load-bearing, and both have tests:

  - Order. Closing the pool before requests drain would turn the last few
  in-flight requests into connection errors — the opposite of graceful.
  - Both steps always run. An HTTP close failure is logged and the pool closes
  anyway. Bailing out early would leak it in exactly the case where something
  has already gone wrong.

  shutdown() returns the exit code instead of calling process.exit, so the logic
  is testable without stubbing process control; attachGracefulShutdown() is
  thin glue.

  Two corrections I made to my own work:

  I commented that closeIdleConnections() was load-bearing, then probed it: with
  a genuinely idle keep-alive socket held open (confirmed via getConnections),
  plain close() still completed in 0ms on Node 24. So it's redundant here, not
  load-bearing. I kept the call — package.json pins no engines, so the deploy
  runtime is an open variable and the call is idempotent — but rewrote the
  comment to say so honestly.

  I'd also generalised the server.on('error') message away from "Failed to bind
  port". That was a regression: that handler fires for listen failures
  (per-connection errors go to clientError), so the original was accurate for
  the case that occurs. Reverted.

  Verification. 122/122 tests pass, typecheck clean across all three workspaces.
  I checked the idempotency test isn't vacuous — disabling the guard fails it
  with 3 exits instead of 1.

  What I could not verify: real OS signal delivery. Windows doesn't deliver
  SIGTERM at all, and child.kill('SIGINT') from Node on Windows hard-terminates
  rather than signalling, so no tool call here can exercise that path. The
  handler wiring is covered by tests; the OS→handler hop is not.

  Two things for you:

  - Your dev server from the earlier session is still running (pid 124316, on
  port 3000, started before these commits). It's running the pre-shutdown code —
  if you Ctrl-C it to try this, you'll see the old behaviour. I left it alone
  rather than killing it.
  - To verify by hand: stop that process, then run npx tsx src/server.ts from
  server/ and Ctrl-C. Not npm run dev — tsx watch intercepts signals to restart
  the child, so it won't exercise the handler cleanly. You should see Received 
  SIGINT, shutting down… then Shutdown complete.

  Task 16 against real Supabase is still the remaining gate, unchanged.
